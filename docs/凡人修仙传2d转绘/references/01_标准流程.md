# 标准流程

## 1. 输入和输出

建议用户提供一个项目根目录，目录下每个片段使用同名子目录，例如：

```text
project_root/
  Merge-001/
    Merge-001.txt
    Merge-001-（000000_000 - 000016_080）.mp4
  Merge-002/
    Merge-002.txt
    Merge-002-（000016_080 - 000031_080）.mp4
```

源视频识别应使用精确规则，而不是递归选择所有 mp4：

```regex
^Merge-\d{3}-（\d{6}_\d{3} - \d{6}_\d{3}）\.mp4$
```

每个片段的正式文本是 `Merge-NNN.txt`。若源视频或文本有多个候选，记录失败并请求确认，不要猜测。最终文件建议放在片段目录根部：

```text
Merge-NNN_{STYLE_TAG}_H3_768p_AI音轨_v1.mp4       # 中间结果，仅留档
Merge-NNN_{STYLE_TAG}_H3_768p_原声音轨_v1.mp4     # 用户成片
Merge-NNN_{STYLE_TAG}_H3_768p_QC_12f_v1.jpg       # 视觉 QC
```

处理资料放在：

```text
Merge-NNN/storyboard_process/
  00_inventory/       # probe、shot 时间
  01_keyframes/       # 原片分析帧
  02_content_grid/    # 原片内容网格，只给 GPT Image 2
  03_gpt_image2/      # 故事板提示词和生成记录
  04_h3_prompt/       # H3 prompt
  05_workflow/        # API workflow
  06_generation/      # H3 原始输出
  07_audio_replace/   # 原音替换中间产物
  08_qc/              # QC 图和结论
  logs/               # prompt_id、technical_qc
```

默认交付规格：`1376×768`、`24 fps`、源音频。若用户明确要求其他规格，先记录规格并同步修改 workflow、QC 阈值和文件名。

## 2. 盘点和源片段分析

对每个源片段运行 `ffprobe -show_streams -show_format -of json`，保存 `00_inventory/probe.json`。至少记录：时长、宽高、帧率、视频编码、音频编码、采样率、声道数。

完整读取 `Merge-NNN.txt`。它是镜头、动作、对白、声音和音乐的权威文本。提取：

- 每个 `[Shot N]` 的起止时间；
- 景别、机位、主体、动作、环境和镜头运动；
- 说话人、逐字台词、画外音和内心独白；
- `overall_soundscape` 和 `non_diegetic_music`。

不要擅自扩写剧情。源画面与文本冲突时，用源画面校正空间和动作；台词以原音和文本复核后的版本为准。

## 3. 抽帧和内容网格

原视频可以抽帧，但抽帧只用于理解内容，不得上传到 H3。优先按每个 Shot 起止时间取 35%–55% 的代表帧；有明显动作转折时每个 Shot 可取两帧。没有可靠 Shot 时间时，均匀抽取 6–12 帧。

把帧拼成内容网格，保存到 `02_content_grid/`。内容网格可以给 GPT Image 2 作为“内容/构图参考”，不能给 H3 作为参考图。

## 4. 风格测试、故事板和风格锁定

不要一开始就对全部片段生成。先选一个能代表主体、动作和场景变化的短片段，必要时再加一个最复杂或最容易暴露问题的片段作为测试。用测试片段做 1–3 轮小样，向用户呈现：内容网格、风格故事板、H3 小样视频、原音合成预览和简短问题清单。只有用户明确确认“按这个风格继续”后，才建立 `style_lock.md` 并开始全量。

每个片段的正式故事板使用两类输入：

1. 当前片段内容网格：保留人物位置、动作、镜头顺序和关键道具；
2. 已锁定风格锚点：定义用户确认过的线条、色彩、材质、构图、光影、人物处理和运动语言。

`style_lock.md` 至少记录：

- 用户选择的风格名称和一句话目标；
- 最终采用的参考图路径/版本；
- 正向风格词：线条、阴影、色块、材质、镜头、运动、光色；
- 负向约束：禁止的写实/3D/细节/文字/水印/色彩问题；
- 用户对测试小样的明确反馈和最终确认时间；
- 768p、fps、音频、命名和 QC 约束；
- 后续只允许的局部修正，以及触发重新测试的重大改风格条件。

故事板必须是原创的宽屏多格构图，面板数与 Shot 数一致，画面中不得出现中文、英文句子、字幕、乱码、水印或 logo。台词查看版另做，不作为 H3 参考图。生成后检查人物身份、动作、左右关系和关键道具，不合格就只针对问题重做一次。

风格锁定时应把用户的自然语言转成可执行要点：

- 线条：例如细线/粗线、干笔/墨线、是否保留铅笔边缘；
- 阴影：例如两阶赛璐璐、柔和厚涂、版画阴影或平涂；
- 色彩：写明主色、强调色、明度和饱和度，不擅自套用其他项目色板；
- 构图：写明景别、留白程度、画面密度、透视和主体位置；
- 运动：写明连续动画、节奏、镜头运动和动作幅度；
- 禁止项：写实、3D、游戏 CG、过密背景、生成文字、异常闪烁等。

若用户尚未指定具体细节，可以把“原创二维剧场动画、手绘线条、简化背景、清晰动作和适度留白”作为待确认的基线，而不是直接锁定为最终风格。

## 5. H3 Ref2VA

H3 prompt 固定使用六段并保持顺序：

```text
subject_definitions
summary
retention_analysis
detailed_description
overall_soundscape
non_diegetic_music
```

参考标签固定为：`<Picture 1>` 是当前片段无台词故事板，`<Subject 1>` 是其中的原创角色/世界和统一二维风格。不得出现 `<Video 1>`，不得把原视频、原始关键帧或音频接入 H3。

`summary` 必须包含 `[reference generation]`。`retention_analysis` 要明确故事板中的镜头顺序、构图、角色身份、动作、色彩节奏 `fully_preserved`，同时明确故事板面板边框、编号和排版不得出现在最终视频。

`detailed_description` 按源文本的时间轴逐 Shot 描述：景别、机位、主体、动作、镜头运动、光色和情绪。写明“连续动画、自然过渡、不是静态图片慢推”。对白可用 `<d>spoken dialogue timing only; never render text</d>` 作为时间提示；画外音写 `off-screen voiceover`，内心独白写 `inner voiceover`，防止错误口型。

全局视觉约束要以 `style_lock.md` 为准，并补充以下跨风格不变量：

```text
[STYLE_LOCK_VISUAL_LANGUAGE]. Preserve the user's chosen value range and palette; keep every frame readable without accidental clipping or muddy exposure. No written characters, subtitles, captions, watermark, logo, or storyboard borders unless the user explicitly requires a separate text layer. No photorealism, glossy CGI, or dense detail unless the locked style explicitly requires it. Maintain a readable final frame; do not fade to black accidentally.
```

## 6. 768p workflow 和生成

以已验证的 H3 API workflow 为模板复制，不直接改原模板。先确认 JSON 是 API 格式（节点对象含 `class_type`），再按当前工作流 schema 注入：

- 故事板路径：只接到 reference image 输入；
- prompt：当前片段六段 H3 prompt；
- width：`1376`；height：`768`；fps：`24`；
- length：`round(source_duration × 24) + 2`；
- seed：用 `base_seed + segment_number` 或其他可复现规则；
- 输出前缀：包含片段名和版本号。

不要凭节点编号假设所有 workflow 都相同；修改前用 API JSON 或 ComfyUI schema 确认字段。保持已验证的模型、采样器、Sage/SolAttn/EasyCache 配置，不要在批量中随意混用不同模型。

ComfyUI 运行前检查 `/system_stats` 和 `/queue`。一次只提交一个片段，立即保存 `prompt_id`，轮询到 success/error 后再进入下一段。H3 原始声音仅留作中间产物，不能交付。

## 7. 替换原音和对齐时长

用 `finalize_video.py`：

1. 探测源视频与 H3 视频时长；
2. 用 `ratio = source_duration / h3_duration` 调整 H3 视频 `setpts=ratio*PTS`；
3. 映射源视频 `1:a:0`，H3 音频不映射；
4. 视频重新编码为 H.264，音频优先 `-c:a copy`；
5. 生成最终片和技术 JSON。

最终音频解码为相同 PCM 后，与源音频分别计算 SHA256。哈希一致是最可靠的音轨核对；如果封装工具造成尾部微差，必须记录实际时长和原因，不能把 H3 音频当作替代方案。

## 8. QC 和返工

技术 QC：可被 ffprobe 读取；`ffmpeg -v error -xerror -i final -f null -` 无错误；尺寸、帧率、音频存在性正确；时长误差在项目阈值内；源/最终 PCM 哈希一致。

视觉 QC：从最终片抽 12 帧拼图，检查是否符合 `style_lock.md`、人物连续性、镜头顺序、字幕/乱码/水印、故事板边框、意外黑尾/过曝、严重肢体/脸部崩坏和是否只是静态图片推拉。

发现字幕或竖幅文字：先修正故事板/H3 prompt 中的文本描述，再重生成；不要默认用模糊遮罩掩盖。发现意外过暗、过亮或黑尾：按 `style_lock.md` 的明度目标修改 prompt，再重生成；不要全片套用固定提亮或压暗滤镜。只有确认是孤立尾帧且用户接受时，才可做可追溯的尾帧修复，并重新 QC。

## 9. 长视频拼接

所有片段通过 QC 后，使用 `concat_videos.py` 按数字顺序拼接。它会再次确认每段的编码、尺寸、帧率和音频参数一致，生成单独的全集文件，不覆盖任何分段成片。拼接后必须对全集运行一次完整 ffmpeg 解码检查，并记录总时长。
